# Part 1: How it works

Read this part when you get stuck. It has the answer to almost every question you will have.

## No gamepad this time

P03 needed WiFi, Chrome and a paired controller. This one needs none of that. Plug the robot into your Mac with the USB cable, run it, and press the pads on the robot itself.

Your file starts the same way P02 did:

```
alvik = ArduinoAlvik()
alvik.begin()
sb = SuperBot(alvik)
```

The sticks are gone, and so is steering. In P03 you told the wheels how fast to spin and you steered by feel. Here you tell the robot how far to go.

## Two commands that measure

Everything in this project is built out of two commands.

```
alvik.move(30)      # drive forward 30 centimeters
alvik.rotate(90)    # turn 90 degrees in place
```

`move()` is in centimeters. `rotate()` is in degrees. Neither one takes a speed, and neither one takes a time. You say how far, and the robot works out the rest.

Both take negative numbers, and a negative means the other way:

```
alvik.move(-30)     # back up 30 centimeters
alvik.rotate(-90)   # turn 90 degrees the other way
```

Which way is `rotate(90)`, left or right? Run it and watch. You will need to know, and finding out takes ten seconds.

## One command at a time

This is the part that is different from everything you have done so far.

In P03, `alvik.set_wheels_speed()` handed the wheels an order and returned immediately. The next line ran while the robot was still rolling. That is why you had to call it every trip around the loop.

`alvik.move()` and `alvik.rotate()` do not work that way. They wait. Write this:

```
alvik.move(30)
alvik.rotate(90)
```

and the robot drives the whole 30 centimeters, stops, and only then starts turning. The second line does not run until the first one has finished. Each command cleans up after itself, too — the wheels are stopped when it hands control back, so you never write a `brake()` inside your route. The one at the bottom of your file, in `finally`, is the same emergency cleanup you wrote in P03, and it stays.

That means a route is just lines in order, top to bottom, exactly the way you read them.

It also means the robot cannot hear you while it moves. Nothing else in your program runs during those 30 centimeters. Touch a pad partway through and nothing happens right then — but if your finger is still on it when the move ends, that pad fires the moment the loop comes back around. Let the robot finish before you touch anything.

## Press a pad on the robot

The robot has six touch pads on its top board: `'up'`, `'down'`, `'left'`, `'right'`, `'ok'` and `'cancel'`. You met them in P01.

You have two ways to ask about a pad. `held()` is True the whole time your finger is down, and you have used it since P01. `pressed()` is True only at the instant you touch it, once per touch — you met that one on the gamepad in P03, and the robot's pads answer to the same two words.

Here you want `pressed()`. A move finishes on its own, so one touch should mean one move. With `held()`, a finger still resting on the pad when the move ends starts the whole thing over again.

```
if sb.pressed('up'):
    alvik.move(30)
    alvik.rotate(90)
```

Your loop runs until you touch Cancel, the same as P02:

```
while not sb.held('cancel'):
```

One difference from P02 is worth knowing. That line only gets asked between moves, and a move can take several seconds. Tap Cancel in the middle of one and the robot will not notice. Hold your finger there until the move ends.

## A patrol is four moves in a row

Here is something worth doing. Drive out, turn all the way around, drive back, turn all the way around again:

```
alvik.move(40)
alvik.rotate(180)
alvik.move(40)
alvik.rotate(180)
```

Four lines, and they have a nice property: if the robot is accurate, it finishes exactly where it started, facing exactly the way it started. You can mark the floor with tape and check.

The patrol is a second thing the robot can do, so it wants a second pad. Put it on LEFT, below the UP block from a moment ago, using `elif` the way P01's colors did:

```
if sb.pressed('up'):
    alvik.move(30)
    alvik.rotate(90)
elif sb.pressed('left'):
    alvik.move(40)
    alvik.rotate(180)
    alvik.move(40)
    alvik.rotate(180)
```

Two pads, and the loop is already ten lines of bare numbers. Add a third pad and it is fifteen. Nothing in there is labeled, so the only way to find the patrol is to read the distances and reason it out.

We need a way to take a group of lines and give it a name.

## Write your own function

Here is that patrol, packed up:

```
def patrol():
    alvik.move(40)
    alvik.rotate(180)
    alvik.move(40)
    alvik.rotate(180)
```

The four lines inside are the four lines you already read. The only new part is the line on top.

`def` is short for define. You saw it on `blink()` in P02. It means "here is a new function, and here is its name." The name here is `patrol`.

The parentheses are empty because this function needs nothing from you. You have seen that before — `alvik.begin()` has empty parentheses too, because there is nothing to tell it.

The `def` line ends with a colon, so the indented lines below it are the function's block, the same as every other block since P01.

Two rules about a function you write.

- **It goes above the loop.** Python reads your file from the top down, and it has to have read the `def` before anything calls it. So all of your functions sit together, near the top, above the `try`.
- **Writing it does not run it.** Python reads the `def`, remembers the name, and moves on. The four lines inside sit there doing nothing until somewhere else in your file says `patrol()`.

And now the chain reads like a list of what the robot can do:

```
elif sb.pressed('left'):
    patrol()
```

## Do the same thing four times

A square is a side and a turn, four times over. Written out the long way, that is eight lines:

```
alvik.move(30)
alvik.rotate(90)
alvik.move(30)
alvik.rotate(90)
alvik.move(30)
alvik.rotate(90)
alvik.move(30)
alvik.rotate(90)
```

You have been here before. In P02 you wrote a blink out three times and then threw it away for a `for` loop, and this is the same trade:

```
for _ in range(4):
    alvik.move(30)
    alvik.rotate(90)
```

Eight lines became three, and now the shape is one number. Change the 4 to a 3 and the same two lines drive a triangle — but only after you fix the turn, because 90 degrees is a square's corner and not a triangle's. Working out the right number is your problem, not mine.

## Make one function do more than one thing

Look at `patrol()` again. It goes out 40 centimeters. It always goes out 40 centimeters. Want a short patrol down a hallway and a long one across the room? You are stuck writing two functions that differ by one number.

Think about `blink()` in P02. You did not have a fast one and a slow one. You had one function, and you told it what you wanted when you called it:

```
blink(3, on_time, off_time, red, green, blue)
```

The values in the parentheses are arguments. You have been handing arguments to other people's functions since P01 — every `alvik.move(30)` you have written today is one. Now you write a function that takes one.

Put a name inside the parentheses of the `def` line, and use that name in place of the number. Here is `patrol()` with the distance pulled out:

```
def patrol(distance):
    alvik.move(distance)
    alvik.rotate(180)
    alvik.move(distance)
    alvik.rotate(180)
```

`distance` holds nothing while the function is just sitting there. It is a promise: whoever calls this function will hand over a number, and inside the function that number goes by the name `distance`. Both `move()` lines use it, so both change together.

So this is a short patrol:

```
patrol(20)
```

and this is a long one:

```
patrol(90)
```

One function, two behaviors, and you never touched the function to get the second one. That is what an argument buys you, and it is why a single `blink()` could give you every color you asked for.

> This one is an example, not an instruction. Leave your `patrol()` alone — WORK 2 wants the plain one. You write a function that takes an argument in WORK 3.

# Part 2: Do the work

WORK 2 and WORK 3 each have two halves. First you write the function, above the loop. Then you go down into the loop and put it on a pad. Do it in that order — a call to a function that does not exist yet is an error.

## Step 1: Set up

1. Turn on your Alvik robot.
2. Connect it to your Mac with the USB cable.
3. Open `p04_move_with_code.py` in Thonny and save your own copy to the robot, as described at the top of this guide.
4. Put the robot on the floor, with about a meter of clear space around it. Not on a table.
5. Get a ruler or a tape measure. You are going to need it.

## Step 2: Type in WORK 1

Drive forward, then turn a corner. That pair of moves is one side of a square, and everything else in this project is built on it.

Find the `# WORK 1` comment inside the loop and type this underneath it:

```
if sb.pressed('up'):
    alvik.move(30)
    alvik.rotate(90)
```

Run it. Line the robot up against something straight, touch UP, and let it finish.

Then measure, because measuring is the whole point of this project.

- How far did it actually go? Write the number down next to 30.
- Did it turn a real right angle, or is it off?
- Which way did `rotate(90)` turn it, left or right?

Touch UP four times in a row and the robot should walk itself around a square and come back to where it started. It probably will not, quite. That gap is what the rest of the project has to live with.

## Step 3: Type in WORK 2

Now your first function, and then the pad that runs it.

Find the `# WORK 2` comment above the loop and type this underneath it:

```
def patrol():
    alvik.move(40)
    alvik.rotate(180)
    alvik.move(40)
    alvik.rotate(180)
```

When you finish the last line, press Backspace until the cursor is back at the left edge.

Run it. Nothing new happens. That is correct — you have written the patrol, but nothing calls it yet.

Now find `# WORK 2 (continued)` inside the loop and add it to the chain:

```
elif sb.pressed('left'):
    patrol()
```

Run it again. Put a piece of tape on the floor at the robot's front edge, touch LEFT, and watch it drive out and come back. It should land on the tape, facing the way it started.

## Step 4: Type in WORK 3

A square, driven by a `for` loop, in a function that takes the length of a side. This one is not printed. You build it out of three pieces you have already seen, and putting them together is the work.

Write it above the loop, under the `# WORK 3` comment. Name it `square`. Three rules:

- Its `def` line takes one argument. Call the argument `side`.
- Inside it, a `for` loop drives one side and turns one corner, four times, so those two lines are written exactly once.
- The line that drives a side uses `side`, not a number. That is the whole point — a number in there would make the argument useless.

Then find `# WORK 3 (continued)` and put it on the RIGHT pad, with a real number in the parentheses:

```
elif sb.pressed('right'):
    square(30)
```

Run it. Then change the 30 to a 15 and run it again. The robot should drive a smaller square without you touching the function at all.

## Step 5: Worksheet and check off

One run shows all three. Touch UP to drive forward and turn, LEFT for the patrol, RIGHT for the square, then hold Cancel to stop.
